# 5G conformance oracle opportunities

Research date: 15 September 2026. Scope: candidate checks for 5G specification conformance and nonconformance, using publicly available ETSI publications of 3GPP specifications. This is a research plan, not an implementation or a finding against any operator.

## What the existing oracle establishes

The repository currently studies one rule in TS 33.501 clause 6.12.3: assignment of a new 5G-GUTI after a paging-triggered Service Request. Its inputs are uplink `RRCSetupRequest` records with a 39-bit `ng-5G-S-TMSI-Part1` and an `establishmentCause`; the DSL offers `distinct`, `constant`, and equality predicates. The local case files expect a violation when that 39-bit value recurs in `mt-Access` requests. This is a useful **screen for possible identity reuse**, but the RRC field is only the rightmost 39 bits of a 5G-S-TMSI, and `mt-Access` alone does not show the Paging message, NAS Service Request, AMF's new full 5G-GUTI, or NAS connection release. A full conformance verdict for that clause needs those events and a reliable way to associate them with the same UE. [TS 38.331, RRCSetupRequest field definition](https://www.etsi.org/deliver/etsi_ts/138300_138399/138331/18.06.00_60/ts_138331v180600p.pdf); [TS 33.501, clause 6.12.3](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf).

The project pins TS 33.501 v17.5.0 for the existing case. The links below use publicly available Release 18 versions for discovery. Before turning any row into an oracle, pin the release/version applicable to the device and network, preserve the exact normative sentence, and inspect relevant exceptions in that version.

## Ranked candidates

“Witness” is an example of evidence that could support a verdict, not a claim that the current captures contain it. **Pass** should mean the required behavior was observed in an applicable, complete episode; **violate** should mean an observed counterexample; **inconclusive** should cover missing context, encryption, unobserved responses, or optional behavior.

| Priority | Candidate and spec anchor | Proposed witness and observation needed | Main qualification |
|---|---|---|---|
| 1 | **GUTI on initial/mobility registration** — AMF sends a new 5G-GUTI during initial registration or mobility registration update. [TS 33.501 §6.12.3](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf) | Decode Registration Request type, successful security activation, Registration Accept/new full 5G-GUTI. Violation: successful applicable registration finishes without a new GUTI. | Needs both NAS directions and end-of-procedure boundaries. Periodic update uses **should**, so it is a separate, weaker candidate. |
| 2 | **GUTI assignment timing** — a new 5G-GUTI is sent only after successful NAS security activation. [TS 33.501 §6.12.3](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf) | Timeline of NAS Security Mode Complete and subsequent GUTI-bearing message. Violation: new GUTI visibly sent before successful activation. | Must distinguish a *new assignment* from an old identity echoed in signaling. |
| 3 | **SUCI placement and SUPI exposure** — SUCI is used only in the specified initial Registration Request, Identity Response, and special De-Registration Request cases; UE does not return SUPI to a permanent-identity Identity Request. [TS 33.501 §§6.12.2, 6.12.4](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf) | Decode NAS identity type and message type. Violation: SUCI in another message, or direct SUPI in an applicable Identity Response. | SUCI's visible home-network fields are intentional. An encrypted NAS payload is inconclusive without lawful endpoint decoding. |
| 4 | **SUCI protection scheme choice** — null scheme is permitted only for specified emergency/provisioning/operator-policy conditions. [TS 33.501 §6.12.2 and Annex C](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf) | Correlate observed SUCI scheme ID with USIM public-key and priority-list provisioning, home-network policy, and emergency status. | A null-scheme SUCI in a passive trace is a **privacy warning**, not automatic nonconformance; the standard allows exceptions and the scheme itself provides no privacy. |
| 5 | **NAS security capability replay** — UE checks the replayed security capabilities in NAS Security Mode Command against what it sent; mismatch leads to Security Mode Reject cause #23. [TS 33.501 §6.7.2](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf); [TS 24.501 §5.4.2.3/5.4.2.5](https://www.etsi.org/deliver/etsi_ts/124500_124599/124501/18.13.00_60/ts_124501v181300p.pdf) | Controlled test changes replayed capability bits, then records UE Reject #23 versus incorrect Complete. | A passive capture usually cannot prove a downgrade attempt; keep normal and perturbed episodes distinct. |
| 6 | **NAS integrity/replay after activation** — once activated, unprotected NAS messages must not be accepted, and each NAS COUNT is accepted only once for the same security context (except null-integrity context). [TS 33.501 §6.4.3.2](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf) | Endpoint/core trace or controlled replay showing NAS security state, COUNT, MAC verification, and receiver acceptance/discard. | On-air presence of an unprotected or repeated PDU does not prove the receiver accepted it; retransmissions and context changes need classification. |
| 7 | **Null NAS integrity restriction** — UE accepts 5G-IA0 only in listed emergency or fixed-access/device cases. [TS 24.501 §5.4.2.3](https://www.etsi.org/deliver/etsi_ts/124500_124599/124501/18.13.00_60/ts_124501v181300p.pdf) | Controlled ordinary mobile registration with Security Mode Command selecting 5G-IA0; observe Reject versus Complete. | Release 18 has several non-emergency fixed-access exceptions; encode the entire applicability clause. |
| 8 | **AS security activation order** — on RRC SecurityModeCommand, UE verifies integrity, sends integrity-protected but unciphered SecurityModeComplete after success, or SecurityModeFailure after failure. [TS 38.331 §5.3.4.3](https://www.etsi.org/deliver/etsi_ts/138300_138399/138331/16.12.00_60/ts_138331v161200p.pdf) | Bidirectional RRC/PDCP trace with AS keys or endpoint verdicts; controlled bad-MAC command tests failure path. | A radio trace without keys cannot verify the MAC. The current CCCH-only decoder does not expose these messages. |
| 9 | **I-RNTI renewal in RRC_INACTIVE** — gNB assigns a new I-RNTI when it requests transition to RRC_INACTIVE during Resume or RNA update, and only after AS security activation. [TS 33.501 §6.12.3](https://www.etsi.org/deliver/etsi_ts/133500_133599/133501/18.11.00_60/ts_133501v181100p.pdf) | Decode RRCResume, RRCRelease/suspend configuration and full I-RNTI for the same UE across cycles. Violation: same assigned I-RNTI after an applicable transition. | Distinguish an old resume identity presented by the UE from a newly assigned one; requires UE linkage and protected RRC messages. |
| 10 | **5GSM invalid session identity handling** — network rejects Modification/Release Request with unassigned or reserved PDU session ID using cause #43. [TS 24.501 §7.3.2](https://www.etsi.org/deliver/etsi_ts/124500_124599/124501/18.13.00_60/ts_124501v181300p.pdf) | Controlled request with known-invalid ID plus downlink Reject/cause. | Maintain session state: an ID is invalid only relative to the receiver's assignments. This is a network conformance test, not a passive privacy metric. |

Other useful domains follow once the above message coverage exists. **Network slicing** can compare Requested/Allowed NSSAI to subscription, tracking-area availability, and roaming mapping, but Allowed NSSAI is not necessarily a subset of Requested NSSAI: the NSSF may add permitted defaults or newly subscribed slices. A naive subset predicate would falsely flag conforming behavior. [TS 23.501 §5.15](https://www.etsi.org/deliver/etsi_ts/123500_123599/123501/18.11.00_60/ts_123501v181100p.pdf). **RRC identity selection** can check whether UE uses `ng-5G-S-TMSI-Part1` when upper layers provide a 5G-S-TMSI and otherwise draws a 39-bit random value, but a capture cannot reveal the upper-layer provision decision; it is best suited to a controlled UE test. [TS 38.331 §5.3.3.3](https://www.etsi.org/deliver/etsi_ts/138300_138399/138331/16.12.00_60/ts_138331v161200p.pdf).

## Suggested first research cases

1. **Registration GUTI assignment**: adjacent to the existing clause and has a clear mandatory trigger/response. Build paired cases for initial and mobility registration, with positive and missing-GUTI episodes. Preserve security-activation timing as an independent oracle.
2. **SUCI message placement**: a compact UE privacy rule with explicit allowed message types. Add separate cases for legitimate initial registration, Identity Response, special De-Registration, and a forbidden placement. Keep null-scheme choice as a policy-informed case.
3. **NAS Security Mode Command capability mismatch**: a strong controlled negative test with an explicit Reject cause. It also tests whether the oracle can represent stateful comparison across messages.
4. **5GSM invalid PDU session ID**: a clear network negative test and a useful expansion beyond privacy/security, once bidirectional NAS and session-state capture are available.

For each case, record: spec release and exact sentence; actor (UE, AMF, gNB, SMF); trigger and exception predicates; required observable events; the positive witness; a finite counterexample; and conditions that force **inconclusive**. Use separate oracles for separate normative sentences. The current DSL and decoder cannot represent these cross-message rules; the table is a backlog for future oracle/capture design, not a claim that they can be run on today's data. In particular, `distinct(39-bit Part1)` is not a substitute for proof that a new full GUTI was sent, and `distinct` cannot test whether a value is unpredictable.
